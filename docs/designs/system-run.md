## Problem Statement
The portfolio already has strong atmosphere and a DeBug-inspired ambient constellation, but its foreground interaction is still primarily a visual trace. The next layer should make the system feel observable and running: a recruiter should understand the story within 10 seconds, while a technical reviewer can explore concrete Android/Linux/security engineering depth.

## What Makes This Cool
The portfolio opens a small, evidence-backed system run rather than presenting a static résumé. A visitor sees stages advance through real project concepts—source, device configuration, kernel/runtime behavior, build, and release—with each state showing one plain-English outcome and a link to verified project evidence. The effect is “I can see how this person thinks through a system,” not just “I can see that they have projects.”

## Constraints
- Keep the current dark visual direction and `AmbientNetwork.tsx` background unchanged in the first slice.
- Optimize for both recruiter clarity and engineering depth.
- Use only verified GitHub/project facts; no invented internship or implementation claims.
- Keep the first implementation reversible and scoped to the existing foreground interaction.
- Preserve responsive behavior, keyboard accessibility, reduced-motion behavior, semantic HTML, and the current Lighthouse-quality baseline.
- Do not add a backend, live GitHub API dependency, actual device flashing, real build execution, fake terminal output, or a 3D scene.
- Keep the existing Astro + React + Framer Motion + Lenis architecture and Netlify deployment.

## Premises
1. The portfolio’s signature should be a live technical system, not another animated résumé.
2. The first 10 seconds should prove engineering depth without making recruiters decode the interface.
3. Each “wow” interaction should connect to real work involving device trees, kernels, release infrastructure, Linux, or security tooling.

## Cross-Model Perspective
The independent review’s strongest proposal was a “bring-up lab”: `source commit → device tree → kernel → power/display behavior → build → signed release → runtime`, with one plain-English outcome and source link per stage. Its key observation was that the builder’s phrase “Show the system running” points to observable state changes and cause-and-effect. It recommended a weekend-sized first slice: a curated `src/data/systemTrace.ts`, a `SystemRun.tsx` component, autoplay/pause/replay, clickable stages, status/timing explanations, and one optional regression branch, while leaving the ambient network unchanged.

## Approaches Considered
### Approach A: System Run — minimal viable
Upgrade the existing foreground panel with 7–8 curated stages, autoplay, pause, replay, clickable stage selection, status badges, timing, “what changed” explanations, and verified GitHub evidence links. Smallest reversible diff; leaves room for a later bring-up lab.

### Approach B: Bring-up Lab — ideal architecture
Create a typed, reusable trace model with dependencies, outcomes, evidence, and explanations, then support multiple system scenarios. Strongest long-term trajectory, but requires more content modeling and more careful first-screen simplification.

### Approach C: Regression Replay — creative/lateral
Add an “Inject regression” path where a visitor watches a missing device-tree node or unsigned release propagate into a failure and recovery state. Most memorable for technical reviewers, but better as a follow-up after the primary run is clear.

## Recommended Approach
Build Approach A first, with the data model shaped so it can grow into Approach B. This is the fastest way to make “Show the system running” tangible while protecting recruiter scanability and keeping the change easy to revert if the interaction does not feel right.

Initial event sequence should be limited to verified claims and may use concepts such as source/project, device configuration, kernel/runtime, build, release, and runtime outcome. Each event needs a short label, a plain-English explanation, a status, a required presentation duration, and a public source link. The duration controls the replay cadence; it is not presented as measured build or runtime performance. Do not imply that the portfolio is executing these processes live; present it as an evidence-backed replay.

## Interaction Contract
- **Initial state and autoplay:** Render stage 0 immediately with the label “System Run / evidence-backed replay,” its plain-English outcome, and its verified source link. Initial autoplay is eligible only while the player is untouched: stage 0 is selected, progress is zero, and the user has not activated any control or stage. Once the panel is at least 50% visible and remains visible for 400 ms, it starts. Any user stage selection or explicit playback action cancels the pending initial start. It advances every stage’s required `durationMs` (target 2200 ms per stage, with the exact value stored in the data model) and does not restart on subsequent scrolls.
- **Visibility suspension:** If the tab or panel leaves visibility while the player is `playing`, record that it was automatically suspended and preserve the current stage and progress. Resume automatically only when visibility returns and no user pause, stage selection, Replay, or other explicit control action occurred while it was hidden. If the player was `idle`, explicitly `paused`, or `complete` when visibility was lost, preserve that state and do not resume automatically.
- **End state:** After the final stage’s duration, playback stops, the player state becomes `complete`, and the final stage remains selected. The control surface exposes Replay; no automatic loop occurs.
- **Pause and resume:** Pause freezes the current stage and its progress indicator. Resume continues from that exact point. Selecting a stage, activating a stage button from the keyboard, or leaving the visible viewport pauses playback so user inspection cannot be interrupted.
- **Replay:** Replay resets to stage 0, clears progress, selects stage 0, and starts playback only when the panel is visible and the user has not requested reduced motion. Otherwise it resets to stage 0 and remains idle for explicit user activation.
- **Stage selection:** Stage buttons select the requested stage immediately, expose its explanation and evidence, and pause playback. Selecting a different stage resets that stage’s elapsed time and progress to zero; selecting the already-active stage preserves its current elapsed time. Selecting any stage after `complete` also resets that target to zero. The player resumes from the selected stage’s remaining duration. The selected/current stage uses a distinct visual and `aria-current="step"` state from upcoming and previously visited stages.
- **Reduced motion:** With `prefers-reduced-motion: reduce`, autoplay is disabled, stage changes are instant, progress does not animate, and the first stage remains visible until the user activates Play or selects a stage. Pause, Replay, and stage selection retain the same semantics without transition effects.
- **Keyboard and assistive technology:** Use native buttons in this tab order: Play/Pause, Replay, then stage buttons in sequence. Enter and Space activate controls. Buttons expose `aria-label`, `aria-pressed` where applicable, and `aria-current="step"` for the selected stage. A polite live region announces the selected stage label and short outcome after user-initiated changes, while automatic playback does not announce every stage. Focus rings remain visible against the dark surface.
- **Status vocabulary:** Keep player state separate from evidence and stage state. Player state is `idle`, `playing`, `paused`, or `complete`; stage state is `upcoming`, `active`, or `visited`; every source badge is `verified` only after the link is checked. Player state describes controls, stage state describes replay progress, and `verified` describes evidence—not build success or failure.
- **Data contract:** Each stage requires `id`, `label`, `summary`, `explanation`, `evidenceHref`, `evidenceLabel`, `durationMs`, and ordered stage data. Any claim about actual runtime/build behavior must be backed by the linked source; presentation duration must never be described as real execution time.

## Success Criteria
- Within the first 10 seconds, a first-time visitor can identify that the panel is a running technical system and understand its current state.
- A technical reviewer can pause, replay, select stages, inspect status/timing, and open evidence links.
- The interaction remains usable with keyboard input and reduced motion enabled.
- Mobile layout has no horizontal overflow and keeps the current responsive hierarchy.
- The build passes, the public page has no console errors, and Lighthouse remains at least 90 in all core categories.
- Every project-specific statement in the run maps to verified research or a public repository source.
- The ambient constellation background and existing page sections remain stable.
